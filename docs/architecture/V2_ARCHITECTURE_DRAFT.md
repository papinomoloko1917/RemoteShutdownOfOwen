# Архитектура RemoteShutdownOfOwen V2 — проект на согласование

**V2 DESIGN / NOT IMPLEMENTED / SIM_ONLY, 11.11.2026.** Не путать предложенную архитектуру с успешно испытанной программой. Источник требований — `ТЗ_...редакция_6_ПРОЕКТ.docx`, прежде всего §§3.1–3.12 и 5.1–5.5. Проектные детали ниже отмечены как `ПРЕДЛОЖЕНИЕ`, а не утверждённый алгоритм.

## 1. Границы оборудования

- КПП: SB1 — штатная дистанционная кнопка; HL1 — индикация на ПУО.
- ЩАОП1: **ПР205-24.1211.02.0.0**; КСН210-2.1 (Ethernet + SFP), резервированное 24 В питание по проекту; HL2/HL3/HL4 на щите.
- Связь: существующая оптика ~600 м, два КСН210-2.1; КСН — **неуправляемый Layer 2**, не источник подтверждения достоверности SB1.
- ЩАОП2: **ПР103-24.1610.03.1.0**, SB3, потенциальное реле K1, модуль измерения МЭ210-701 (физически ещё не испытан).
- Действующий ЩАО/АВР/ДГУ: собственный алгоритм **не изменяется**. SB2 — независимая штатная кнопка разрыва существующей цепи. Новая система не должна шунтировать SB2.

## 2. Функциональные слои

```text
[ПР205] Физический SB1 + фильтрация -> команда и диагностический кадр
                            |
                     Modbus TCP Slave
                            |
                  КСН210 — оптика — КСН210
                            |
                     Modbus TCP Master
                            |
[ПР103]  1. Статус устройства + валидность данных / тайм-аут
         2. Установление режима REMOTE / LOSS_LOCK / LOCAL / RECOVERY_WAIT
         3. Состояние SB1 и защитная команда STOP_REQUEST (логическая)
         4. Отдельный RELEASE_PERMISSION (только в разрешённых сценариях)
                            |
                  K1: ФИЗИЧЕСКАЯ ЧАСТЬ НЕ ПРОЕКТИРОВАНА
```

Никакая диагностика по одному пакету не доказывает отсутствие опасного отказа. `ModbusOK`, `DATA_VALID`, `STOP=0`, `RELEASE_PERMISSION` и `MODE` — **разные** сигналы.

## 3. Стратегия реализации (ПРЕДЛОЖЕНИЕ)

### ПР205

- Физическая SB1 -> фильтр -> один согласованный выходной сетевой снимок команды.
- Использование уже изученного диагностического кадра `SB1_FRAME_TX = 2×HB+STOP` (DEC 16389) допустимо **как диагностика**, не как математическое доказательство свежести после restart/wrap.
- Контроллер не должен сам управлять K1/LOCAL/ЩАО; не добавлять фиктивные связи к Q для симуляции.
- Экспериментальные `KPP_CHALLENGE_RX` 16390 и `SB1_ACK_FRAME_TX` 16391 сохранить только в историческом V1. Никакого автоматического переноса этих цепей в новую FBD без отдельного решения.

### ПР103

- Использовать `Статус` Master для `KPP_MODBUS_OK`, а не самодельный TCP watchdog. Фактически такой статус уже имеется в старой FBD.
- Отдельно контролировать срок/монотонность/валидность кадра SB1. Положительный heartbeat без независимого подтверждения не снимает lock/LOCAL.
- Состояния `REMOTE`, `LOSS_LOCK`, `LOCAL`, `RECOVERY_WAIT` определить единой таблицей, а не разрозненными reset SR/TON. См. `OPERATING_MODES_V2.md`.
- Разнести вычисления `STOP_REQUEST`, `RELEASE_PERMISSION`, `DISPLAY_STATUS` и `VOLTAGE_ABSENCE_CONFIRMED`.
- Физическую карту Q/NO/NC/K1 не задавать до утверждённой электрической схемы и оценки опасных отказов.

## 4. Два режима требований к свежести

**Путь A, ПРЕДЛОЖЕНИЕ для V2:** исключить автоматический сброс аварийных блокировок после нарушений, рестартов и LOCAL; снятие требует специальной согласованной процедуры. Штатная связь+heartbeat может служить ограниченным диагностическим признаком в непрерывном REMOTE, однако сама не исключает незамеченного рестарта и повтора. Строгая гарантия `STOP=0` при небезопасных последствиях не может опираться только на HB.

**Путь B, если требуется автоматический выход из неопределённости:** отдельный протокол подтверждения свежести с защищённой от повтора сессией/эпохой обоих ПР; программно проверить в SIM, аппаратно на изолированном стенде; энергонезависимость/переполнение/сетевые задержки должны быть доказаны. P03/P04-01 не доказывают Путь B; P04-02 обнаружил отказ.

**Ни один путь не является утверждённой функцией функциональной безопасности.** Выбор пути и допустимость переходов должны быть согласованы до программирования разрешений, особенно учитывая потенциальное автоматическое восстановление питания по алгоритму ЩАО.

## 5. Отношение к примерам ОВЕН

Пример `2 ввода на общую шину.owle` (Owen Logic 2.7.350; иная модификация ПР205) демонстрирует разделение команд/состояний, фильтрацию входов, выдержки, взаимные запреты. **Не** является готовой программой дистанционной SB1/SB3.

`Counter.owl` и `description_counter.docx` — учебный пример счётчиков CT/CTN/CTU для ПР200/старой версии Owen Logic. Счётчик пригоден для диагностики, **не** гарантирует уникальность запросов после reboot. Не вставлять проект целиком.

## 6. Условия запрещённых переходов

- `LOCAL=1` + старое `STOP=0` + изменился HB/`MODBUS_OK=1` -> **НЕЛЬЗЯ** выходить из LOCAL / сбрасывать lock.
- Запуск/рестарт ПР103 или ПР205 -> **НЕЛЬЗЯ** считать старый `STOP=0` новым разрешением.
- Потеря связи -> защитный запрос отключения, кроме санкционированного LOCAL по процедуре.
- Удержанная при включении питания SB3 -> **НЕ** новый сознательный запрос местного разрешения.
- `VOLTAGE_ABSENCE_CONFIRMED` -> только реальные достоверные измерения **всех трёх фаз** МЭ210, не из STOP/K1.
